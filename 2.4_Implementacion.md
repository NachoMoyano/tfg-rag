# 2.4. IMPLEMENTACIÓN

Esta sección describe la materialización en código del diseño presentado en la
sección 2.3. La implementación traduce los componentes de la arquitectura
(sección 2.2) en módulos de software independientes y débilmente acoplados, de
forma que cada uno asume una única responsabilidad y se comunica con el resto a
través de interfaces bien definidas. El sistema completo se ejecuta de forma
local, sin dependencias de servicios en la nube, cumpliendo así el requisito
RNF-04.

## 2.4.1. Entorno tecnológico y organización del código

El sistema se ha desarrollado íntegramente en *Python* 〔versión: indicar, p. ej.
3.11〕 y se apoya en las siguientes tecnologías, todas de código abierto o de
ejecución local:

- *Flask* como microframework para la API orquestadora (servidor central).
- *Streamlit* para la interfaz de usuario web.
- *ChromaDB* como base de datos vectorial, en modo persistente sobre disco.
- *SQLite* (módulo `sqlite3` de la biblioteca estándar) como base de datos
  relacional de operación.
- *LM Studio* como servidor de inferencia local, que expone el modelo de
  lenguaje a través de una API compatible con el estándar de *OpenAI*.
- La biblioteca *sentence-transformers* con el modelo `all-MiniLM-L6-v2` para la
  generación de *embeddings*.

El código se ha organizado en módulos separados según la responsabilidad de cada
componente 〔ajustar a tu estructura real de ficheros/carpetas; p. ej. `app.py`
para la API, `router.py` para el enrutador, `retriever.py` para la recuperación,
`db.py` para la persistencia, `ingest.py` para la ingesta y `ui.py` para
Streamlit〕. Esta separación permite probar y modificar cada pieza de forma
aislada, y refleja directamente la arquitectura descrita en la sección 2.2.

## 2.4.2. Proceso de ingesta y vectorización

La construcción de la base de conocimiento es un proceso *offline* que se ejecuta
una sola vez (o cada vez que se actualiza el catálogo), independiente del flujo
de consulta en tiempo de ejecución. Su objetivo es transformar las fuentes
heterogéneas descritas en el objetivo 1 en las dos colecciones de ChromaDB
definidas en el diseño.

El conocimiento teórico, redactado en formato *Markdown*, se fragmenta
(*chunking*) respetando su estructura: cada documento se divide primero por
secciones (encabezados `##`) y, dentro de cada sección, en sub-fragmentos cuando
el texto supera 〔indicar el tamaño máximo de *chunk* empleado, p. ej. en número
de caracteres o de *tokens*〕. Este criterio busca el equilibrio descrito en la
sección 1.3.4: fragmentos lo bastante grandes para preservar el contexto
semántico, pero no tanto como para introducir ruido en el contexto del modelo.
Cada fragmento resultante se almacena en la colección `general_knowledge` con un
identificador de la forma `teoria_<hash>` 〔confirmar cómo generas el hash, p. ej.
los primeros 8 caracteres de un *hash* SHA-256 del contenido〕 y los metadatos
`source`, `tipo`, `seccion_idx`, `sub_chunk_idx` y `texto_original`.

Los productos del catálogo siguen un tratamiento distinto. Para cada producto se
construye un único documento de *embedding* que concatena el título, el proveedor
y un resumen de la descripción 〔confirmar el recorte, p. ej. los primeros 300
caracteres〕, de modo que el vector capture la información más distintiva del
producto. La descripción corta y la descripción larga completa se conservan como
metadatos (`descripcion_corta` y `descripcion_larga`) para poder devolver el
nivel de detalle adecuado según el tipo de consulta. Estos documentos se indexan
en la colección `products_catalog` con identificadores de la forma `prod_<hash>`.

Ambas colecciones se vectorizan con el modelo `all-MiniLM-L6-v2`, garantizando
que documentos almacenados y consultas entrantes se proyecten al mismo espacio
vectorial y puedan compararse por similitud semántica.

## 2.4.3. El orquestador: API en Flask

El orquestador es el componente central y el único conectado a todos los demás.
Se implementa como una API REST en *Flask* que expone un endpoint principal
〔p. ej. `POST /chat`〕 que recibe un cuerpo JSON con la pregunta del usuario y el
identificador de sesión:

```json
{ "pregunta": "¿Tenéis datasets sobre el mercado laboral?", "session_id": "..." }
```

Al recibir una petición, el orquestador ejecuta de forma secuencial el flujo que
da soporte a los casos de uso CU-01, CU-02 y CU-03:

1. Valida que la petición cumple el formato esperado (RF previo a cualquier
   búsqueda).
2. Invoca al **enrutador semántico** para clasificar la intención del usuario
   (RF-04).
3. Recupera de SQLite el historial reciente de la sesión para dotar al asistente
   de memoria conversacional (RF-06).
4. Consulta la colección de ChromaDB correspondiente a la categoría detectada y
   recupera los fragmentos más relevantes (RF-05).
5. Construye el *prompt* aumentado combinando instrucciones de sistema, historial,
   contexto recuperado y pregunta.
6. Envía el *prompt* al servidor LLM y obtiene la respuesta generada.
7. Persiste el intercambio (pregunta y respuesta) en SQLite y registra los
   eventos del proceso en la tabla de *logs*.
8. Devuelve a la interfaz la respuesta final junto con las fuentes utilizadas
   (RF-07).

## 2.4.4. El enrutador semántico

El enrutador semántico es la primera de las dos invocaciones al LLM por cada
pregunta. Su función es clasificar la intención del usuario en una de las tres
categorías —`GENERAL`, `CATALOGO_BUSQUEDA` o `CATALOGO_DETALLE`— antes de lanzar
ninguna búsqueda, lo que permite seleccionar la colección y el número de
resultados adecuados y optimizar el uso de recursos de la máquina local.

Para que la clasificación sea precisa y, sobre todo, determinista, se emplea la
técnica de *Few-Shot Prompting*: el *prompt* de clasificación incluye varios
ejemplos de preguntas ya etiquetadas que fijan el patrón esperado, y la
temperatura del modelo se establece en `0.0`, eliminando cualquier aleatoriedad
en la decisión. El *prompt* tiene una estructura similar a la siguiente
〔adaptar al texto exacto que uses〕:

```text
Clasifica la intención del usuario en una de estas categorías:
GENERAL, CATALOGO_BUSQUEDA o CATALOGO_DETALLE.
Responde únicamente con la etiqueta, sin texto adicional.

Ejemplos:
"¿Qué es la k-anonymity?" -> GENERAL
"¿Tenéis datasets sobre el mercado laboral?" -> CATALOGO_BUSQUEDA
"Dame los detalles del Synthetic Data Pack" -> CATALOGO_DETALLE
[...]

Pregunta: "{pregunta_usuario}"
Categoría:
```

Dado que el modelo podría, en casos límite, devolver una etiqueta inesperada, la
salida se valida contra el conjunto de categorías permitidas y, si no coincide
con ninguna, se aplica una categoría por defecto 〔indicar cuál, p. ej. `GENERAL`〕
para garantizar la robustez del sistema.

## 2.4.5. Recuperación y construcción del *prompt* aumentado

Una vez clasificada la intención, el orquestador traduce la categoría a una
configuración de recuperación concreta sobre ChromaDB:

| Categoría | Colección | Nº de resultados |
|---|---|---|
| `GENERAL` | `general_knowledge` | 3 |
| `CATALOGO_BUSQUEDA` | `products_catalog` | 5 |
| `CATALOGO_DETALLE` | `products_catalog` | 1 |

La pregunta del usuario se vectoriza con el mismo modelo de *embeddings* y se
lanza una búsqueda por similitud, de la que se obtienen los fragmentos (y sus
metadatos) más próximos. En las consultas de catálogo, los metadatos recuperados
varían según el caso: para `CATALOGO_BUSQUEDA` se utilizan título, proveedor y
descripción corta; para `CATALOGO_DETALLE`, título, proveedor y descripción
larga completa.

Con esta información se ensambla el *prompt* aumentado que recibirá el LLM, cuya
plantilla se adapta a la categoría detectada (por ejemplo, instruyendo al modelo
para responder como consultor experto en las consultas generales, o para
presentar los resultados en formato de tabla en las búsquedas de catálogo). La
estructura general del *prompt* es:

```text
[Instrucciones de sistema adaptadas a la categoría]
[Historial reciente de la conversación recuperado de SQLite]
[Contexto: fragmentos recuperados de ChromaDB]
[Pregunta original del usuario]
```

Para evitar los problemas de hardware mencionados en el objetivo 4 —en
particular, los desbordamientos de memoria en la GPU al exceder la ventana de
contexto del modelo—, se aplican límites estrictos sobre la longitud del texto
inyectado. Antes de enviar el *prompt*, tanto el contexto recuperado como el
historial se truncan para no superar 〔indicar el límite de contexto que fijaste,
p. ej. en *tokens* o caracteres〕, priorizando los fragmentos más relevantes y
los mensajes más recientes.

## 2.4.6. Generación con el LLM local

La segunda invocación al servidor LLM es la que genera la respuesta final. El
orquestador envía el *prompt* aumentado al endpoint de *chat completions* que
expone *LM Studio*, aprovechando su compatibilidad con la API de *OpenAI*: esto
permite reutilizar el cliente estándar y desacoplar el orquestador del modelo
concreto que se esté ejecutando 〔indicar el modelo empleado, p. ej.
nombre y tamaño/cuantización: …〕. Al estar el modelo obligado a responder
basándose únicamente en el contexto recuperado, se reduce de forma drástica el
riesgo de alucinaciones, en línea con la justificación de la arquitectura RAG de
la sección 1.3.4.

De la respuesta y de los metadatos de los documentos recuperados se extraen las
fuentes que se mostrarán al usuario, dando cumplimiento al requisito RF-07.

## 2.4.7. Persistencia: historial y *logs* (SQLite)

La persistencia se implementa sobre SQLite con las dos tablas definidas en el
diseño (sección 2.3.1). La tabla `historial_chat` almacena cada mensaje de la
conversación —tanto los del usuario como los del asistente— asociado a su
`session_id`, lo que permite reconstruir el contexto del diálogo sin necesidad de
una tabla de sesiones separada. En cada turno, el orquestador inserta primero el
mensaje del usuario y, tras generar la respuesta, el del asistente; y recupera
los últimos 〔indicar N〕 mensajes de la sesión para construir la memoria
conversacional.

```sql
INSERT INTO historial_chat (session_id, rol, contenido, timestamp)
VALUES (?, ?, ?, ?);

SELECT rol, contenido FROM historial_chat
WHERE session_id = ?
ORDER BY timestamp DESC
LIMIT ?;
```

La tabla `logs_sistema` registra los eventos internos del proceso (nivel de
severidad, mensaje y marca temporal), lo que facilita revisar el rendimiento del
sistema y diagnosticar errores durante el desarrollo y la evaluación.

## 2.4.8. Interfaz de usuario (Streamlit)

La interfaz se ha desarrollado con *Streamlit* y presenta al usuario un entorno
de chat conversacional que oculta toda la complejidad del sistema RAG. Al iniciar
una conversación se genera un `session_id` 〔p. ej. mediante `uuid`〕 que se
conserva en el estado de sesión de Streamlit (`st.session_state`) durante toda la
interacción, de modo que el hilo de la conversación no se pierde entre mensajes.

Cuando el usuario envía una pregunta, la interfaz la empaqueta junto al
`session_id` en formato JSON y la envía a la API. Al recibir la respuesta, la
muestra de forma ordenada en el historial de chat y presenta las fuentes
utilizadas 〔indicar cómo: p. ej. en un componente desplegable (`st.expander`)〕,
cerrando así el ciclo de la conversación.
